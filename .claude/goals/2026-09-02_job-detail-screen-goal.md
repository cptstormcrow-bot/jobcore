# Job Details Screen Restyle: Goal Description

## 1. Purpose

Restyle `app/apps/mobile/app/job/[jobId].tsx` so one persistent top action-button row drives the job's full lifecycle (Plan through Payment) without ever leaving the screen, replacing today's full-screen panel swaps and inconsistent styling with a compact summary block, a fixed button row, and a full detail form under one typography and spacing system, all within a single unified, single-scroll screen. [NEW: the first iteration of this spec described a split screen with two panes and two scroll bars; the owner has since directed that it be one unified single-scroll screen, and this document reflects only the unified target.]

## 2. Current state

- Route file `app/apps/mobile/app/job/[jobId].tsx` (911 lines) renders the edit-mode "details" view plus six other full-screen sub-panels.
- `activePanel` (7 values: details, plan, jobEstimate, jobInvestigation, schedule, start-checklist, completion) is seeded once from a `panel` deep-link query param, default `details`. Changing it swaps the entire screen for a standalone sub-view, each in its own `<View style={styles.root}>`; the button row and details content disappear while a sub-panel is open, and each sub-view returns via its own `onBack`/`onDone` callback wired to `setActivePanel('details')`.
- Eight JobActions exist today across two role-based embedded components, none enumerated directly in `job/[jobId].tsx` itself. `JobDetail.tsx` (admin/office role) defines Plan, Estimate, Save (`handleSaveEdit`), Close Out & Mark Paid, View Price Sheet, and Add Pay Period Note (6 actions). `FieldJobDetail.tsx` (tech role) defines Start Time and Stop Time as two distinct actions (2 actions), for a total of 8. Save is the only save trigger anywhere in the form; no autosave or on-blur/on-unmount save exists.
- `JobDetail.tsx` is also stateful beyond the JobActions above: a `useEffect`/`Promise.all` independently fetches and renders five further Supabase-backed sections (Materials, Reference Links, Photos with signed URLs from the `job-photos` storage bucket, Notes with a kind badge, and Payments), plus a `JOB_STATUS_COLORS`-driven status bar and a conditional `job.isBeta` "BETA" badge. None of these are placed by the owner's spec; see Open decision 13.
- The Breadcrumb component renders two segments: "Jobs" (navigates back) and `job.address`, falling back to the literal text "Job Details" when no address is set; the current/last segment is never pressable.
- Tech assignment today is a `ListItem`-per-tech row with an inline Assign button, not a dropdown, plus a static "Currently assigned: <name>" line above the list.
- `typography.fontFamily` in `app/packages/ui/src/tokens.ts` defines three keys (`heading` = Poppins, `body` = Inter, `accent` = DancingScript, the last declared but unused in source), all sans-serif except the unused accent; sizes run h1 through h6/body/label/small (40px down to 13px, no 8pt or 10pt value); no serif family is defined, and the mobile app has no font-loading package wired up for any of the three, so none is confirmed to actually render as intended today.
- Button color is role-based, not selection-based: tech role renders `colors.info` (blue), admin/office renders `colors.secondaryDark` (orange), applied uniformly to every button regardless of which panel is open.
- `JobDetail.tsx`'s internal heading text, button order, and full layout beyond the two bullets above are not verified and must be read in full before finalizing the embedding and button-order changes in §3.
- E-visit (formerly labeled "Investigation") is a Segway-tech pre-install fact-finding form (Ingress/Logistics/Parking notes plus a State assessment), one row per job, gated by RLS to whoever holds an "investigator"-kind `job_assignments` row. Its entry action lives only in the field-tech module's own action list, not in this file's button set, and `assignInvestigator()` (the flow that would grant a tech investigator access) has no live caller anywhere in the app (assign-investigator.ts:47), so in practice no tech can currently pass that RLS check.

## 4. Interaction rules

- The button row persists identically no matter what content is showing: all 9 buttons (Plan, E-visit, Estimate, Assign, Schedule, Contact, Arrive, Complete, Payment) stay visible and tappable no matter which one is open. This requires re-architecting `activePanel` from "replace the whole screen" to "render the selected content below a persistent summary block, rule, and button row, all within one unified, single-scroll screen." The content region is one dynamic area: it defaults to the Details fields (§3.4), and selecting Plan, E-visit, Estimate, Assign, or Schedule swaps it to that content in place, reusing the existing `onBack`/`onDone`-to-`setActivePanel('details')` pattern (§2) to return to Details instead of leaving the route or opening a second scroll. Contact, Arrive, Complete, and Payment have no dedicated content of their own and never swap the content region; they perform their write in place.
- The selected button is orange only for Plan, E-visit, Estimate, Assign, or Schedule, whichever one's content currently occupies the content region; every other panel button is neutral. Contact, Arrive, Complete, and Payment have no persistent state to represent and never hold the orange style, only a transient pressed style. This replaces today's static role-based coloring (§2) with selection-driven coloring; see Open decision 16 for a second, unresolved orange-trigger condition.
- No "Back to Job" control exists anywhere; every button switches the visible content in place and never navigates away from `/job/[jobId]`. The Back-to-Job/Back-to-job-list buttons currently built into JobScheduleScreen, PlanningScreen, JobEstimateScreen/Editor, JobInvestigationScreen, StartChecklist, and Completion exist today because those screens are full-screen replacements; they become unnecessary once their content is embedded in the content region of the single unified screen instead.
- Save follows selection: leaving the Details content, or navigating away from the route, triggers `handleSaveEdit` automatically; the explicit Save button is removed (§6).
- Each fact is stated once across the whole screen in full; the summary-block items are treated as an abbreviated summary of the same detail-form facts, not the duplication the owner asked to avoid, see Open decision 12 for confirmation of that reading. The existing separate "Currently assigned" line and tech-picker list are two renderings of one fact and must collapse to one; a prior slice already trimmed this once (`.claude/plans/job-detail-top-action-row-breadcrumb-assigned-tech-summary.md`, Slice 5) and its current state should be confirmed rather than redone.

## 5. Typography and spacing rules

- Proposed size: 8pt for every summary-block and detail-form line, pending confirmation, see Open decision 10, which also covers whether the owner's spec intends 8pt uniformly or 8pt summary block/10pt detail form.
- Headings: bold, gray, serif, title case, at the resolved size. Field values (information): normal weight, black, sans-serif, at the resolved size.
- pt is used here interchangeably with the unitless px sizing already used in `tokens.ts`; no unit conversion is implied.
- No 8pt/10pt size token and no serif family exist in `tokens.ts` today (§2); both a new size token and a new serif token, plus real font loading via `expo-font` (already a dependency) with bundled font files, are required before this rule can render as specified. Whether that font-loading work is in scope for this pass is Open decision 11.
- Button labels stay sans-serif; Button and Breadcrumb already use `fontFamily.heading` (Poppins) for their labels, so no change is needed there. Which component renders the new "Job Details" heading itself (a new component, or reusing ScreenTitle) is not verified; confirm once `JobDetail.tsx` is read in full (§2).
- Whitespace between summary-block lines must be minimized ("very close together but readable"), and text must remain legible at the resolved size with every control reachable and operable, per the owner's "text large enough to read" and "get at everything easily" instructions. Current field spacing uses `spacing.md` (16px); a prior, unconfirmed plan (`.claude/plans/job-detail-screen-formatting-scroll-fix.md`) already reduced field spacing to `spacing.sm` (8px) and redesigned the Rooms grid to 2-column flex-wrap. Confirm whether it was applied before repeating that work.
- Buttons keep the existing 44px minimum height (a permanent 2026-08-30 decision across all `Button` size variants) regardless of how tightly they are packed. A shrunk checkbox keeping an 8px `hitSlop` to preserve its tap target is a document-suggested implementation detail here, not an owner requirement.

## 7. Data and backend requirements

- Job number: no `jobNumber` field exists anywhere in the data model (zero hits for jobNumber/job_number/jobNo repo-wide). A new column, type field, and display value are needed before the breadcrumb can append one. A separate, existing "Job #XXXX" title string (`JobDetail.tsx` line 144, the last 4 characters of `job.id`, uppercased) is addressed in Open decision 2, not this bullet.
- Five job-detail fields (`permitStatus`, `parkingAvailable`, `rooms`, `panelInfo`, `considerations`) are declared in `JobDetailsPatch`/`JobRow` but confirmed dropped on write: `updateDetails()`/`create()` in `app/apps/mobile/src/lib/admin-finance-repos.ts` never reference any of the 5 fields. They are also confirmed dropped on read: `toJob()` in `app/modules/admin-finance/src/data/ports.ts` (line 90) never maps `rooms`, `considerations`, `permit_status`, `parking_available`, or `panel_info` back onto the returned Job object. A fix is already planned at `.claude/plans/fix-5-job-detail-fields-silently-dropped-on-save.md`; its completion is unconfirmed and must be verified or applied, since styling fields that never save has no value. `permitStatus` shares this bug but has no owner-specified place in §3's layout, so it is resolved here as out of this restyle's UI scope.
- Service-area auto-selection: `service_areas` has only `id`/`organization_id`/`name`/`created_at`, no city/zip/boundary columns anywhere. This needs new location columns on `service_areas` plus a matching function before address-to-area derivation can exist.
- Assign dropdown: no `<Select>`-style tech picker exists for job assignment. The one real `<Select>` of techs is the calendar view's tech filter, a different control; building the Assign button's dropdown means either adapting that pattern or building a new UI callback, `handleAssignTech`, that invokes the existing `assignJob()` on selection.
- Calendar/time picker: no calendar-popover or combined date-and-time picker component or library exists in the repo. `JobScheduleScreen.tsx` uses a text-entry DatePicker plus a separate text input; a true picker is a new library or component.
- Elapsed-time counter: no `setInterval`-based timer or duration UI exists anywhere. Arrive/Complete's counting-up display and "start plus elapsed equals stop" are new client-side logic computed from `in_progress_at`/`completed_at`.
- Contact texting: no SMS/text capability exists anywhere in the codebase. Only `telUrl()`, a `tel:` link helper, exists, and it is not currently imported into this route file.
- Mark Paid duplication: see §3.3's Payment row for the two existing call sites and their consolidation to one `transitionJob(job,'paid',ctx)` call.
- `JobDetail.tsx` must be read in full before finalizing the panel-embedding and button-order changes; see §2.
- Plan pulls from E-visit [NEW]: the Plan panel must read the `job_investigations` record for the same job and show Ingress notes, Logistics notes, Parking notes, and State assessment as they are filled in; a partially filled E-visit shows whatever exists so far. No reader exists today [MISSING] — `JobInvestigationScreen.tsx:65` is the only reader of `job_investigations` anywhere in the app; the Plan panel ([jobId].tsx:491) reads nothing from it.

## 8. Open decisions

1. Job number does not exist in the data model. Recommended default: add a short, human-facing sequential column and surface it read-only in the breadcrumb; until added, the breadcrumb keeps its current two segments.
2. "Remove Job ##### entirely from the page": `JobDetail.tsx` line 144 renders an existing "Job #XXXX" title (the last 4 characters of `job.id`, uppercased); this is most likely what the owner is referring to, not an absent string. This is separate from decision 1's `jobNumber` field, which does not exist anywhere in the codebase. Recommended default: remove this title string during the restyle, since the breadcrumb (§3.1 item 1) and decision 1 already cover job-number display going forward.
3. Estimate's "customer accepts" step has no accept control anywhere; acceptance is verbal, followed by a separate admin-only Approve Estimate action registered outside `JobEstimateScreen.tsx`. Recommended default: fold that approve action into the Estimate panel itself rather than adding a ninth top-row button.
4. Assign is requested as new, but a working `assignJob()` write path and an unrelated, dead `assignInvestigator()` already exist. Recommended default: the new Assign button calls `assignJob()`; leave `assignInvestigator()` untouched, pending decision 9.
5. Schedule is requested as new, but `JobScheduleScreen.tsx` (full read/write, validated) already exists with no calendar-popover UI and no button opening it. Recommended default: reuse its save logic, wire a new top-row button to it, and swap its text-entry DatePicker for a calendar/time-picker component chosen during implementation planning.
6. Payment ("use existing Mark Paid") while Close Out & Mark Paid is removed: see §6 for why nothing behavioral needs salvaging from it. Recommended default: leave `closeOutJob()` unwired; Payment calls the same `transitionJob(job,'paid',ctx)` path described in §3.3.
7. Arrive/Complete timestamp mapping: `jobs` has `en_route_at`, `in_progress_at`, `completed_at`, all tech-writable per RLS. Recommended default: Contact sets `en_route_at`, Arrive sets `in_progress_at`, Complete sets `completed_at`; elapsed time is computed client-side, never a stored duration column.
8. Contact "texts" the tech or customer: no SMS capability exists in this codebase. Recommended default: Contact offers a call action only, reusing `telUrl()`; texting is deferred until an SMS approach is chosen.
9. Plan display of E-visit fields: read-only mirror or pre-filled editable copy? Jeff's decision requires the data to appear; the mode is undecided.
10. 10pt vs 8pt text: the owner's opening paragraph gives 10pt generally; the later, screen-specific paragraph gives an explicit 8pt figure for the summary block only and describes the detail form merely as "(Same styling)". Two readings are both spec-supported: (a) 8pt uniformly across the whole screen, the proposed default in §5, or (b) 8pt summary block, 10pt detail form. Recommended default: (a), for visual consistency on one screen; confirm given no 8pt/10pt token exists yet and small text may strain legibility on some devices.
11. The Headings rule (§5) requires a serif face, but no serif family exists in `tokens.ts` today (only Poppins and Inter, both sans-serif) and no font-loading package is wired up for any of the three declared families. Recommended default: add a new serif token plus `expo-font` bundling of font files if in scope for this pass; otherwise substitute a bold sans-serif heading using the existing heading (Poppins) token.
12. The owner's spec lists Customer name and phone in the summary block (§3.1 items 3-4) and again in the detail form (§3.4 items 1 and 3), immediately after instructing that detail-form content not be duplicated. The same duplication exists between §3.1 item 5 "Jobsite address" and §3.4 item 2 "Customer Address": summary block abbreviated, detail form full, or drop one. Recommended default: treat the summary-block items as an abbreviated summary, name/phone/address only, and keep the full field set in the detail form; this reading is what §4 currently assumes.
13. `JobDetail.tsx` also renders Materials, Reference Links, Photos, Notes, and Payment sections, plus a status-color bar and a conditional BETA badge, none of which the owner's spec mentions or places. Recommended default: keep all of them unchanged in content, appended to the bottom of the detail form below Considerations (§3.4 item 10), pending the owner's confirmation of where they belong.
14. Assign picker vs investigator: assignJob and assignInvestigator write the same job_assignments table differing only by kind (assign-investigator.ts:47 vs assign-job.ts:127-131); assignInvestigator has no caller. Decide whether the new Assign dropdown also sets the E-visit investigator (same tech, second assignment row) or a separate picker is added. Code does not settle it.
15. Parking source of truth: jobs.parking_available (migration 0030, written at [jobId].tsx:341) and job_investigations.parking_notes (written at admin-finance-repos.ts:2063) are unreconciled. Decide which the summary block and the detail-form Parking line show, or whether the detail form shows both labeled.
16. Orange rule second condition: the original spec also colors orange any button usable without losing focus on the job screen (not only the active content's button). §4 currently states only the active-content rule. Decide whether Contact/Arrive/Complete/Payment are orange under that second condition.
17. Whether the summary block and button row stay pinned at the top of the screen while the content region scrolls beneath them, or the whole screen scrolls as one unit with no pinned elements. Undecided; a pinned header is the common mobile pattern and is offered here as a recommendation, but the choice is the owner's call.
