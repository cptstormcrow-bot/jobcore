Chapter 6 — Payment & Review

Registered, Not in Menu

The payment-review module is registered in apps/mobile/src/modules.ts (owner/admin only) but is not listed in the logo menu. Owners and admins reach its Reconciliation view via Admin Finance → Review, and it still opens directly at /m/payment-review.

This is a deliberate consequence of the two-axis gating model introduced in Chapter 1, "What Is JobCore?": a module must clear axis 1 (compile-time registration) before axis 2 (runtime per-organization enablement) is even relevant. apps/mobile/src/modules.ts is the single file permitted to name a specific module and currently imports and registers all four modules: adminFinanceModule, fieldTechModule, salesMarketingModule, and paymentReviewModule, which is left out of the logo menu on purpose. This chapter is architecture-and-status only: no "A Typical Day" persona narrative and no "Try It" section, per the pattern set in Chapters 3–5.

What the Module Contains

Although it is not in the logo menu, modules/payment-review/src/ is a substantially built module, not a stub. It exposes:

  • Payment method providers — domain/providers/ implements cash.ts, check.ts, p2p-link.ts (Venmo-style peer transfer), paypal.ts, and stripe-link.ts (card). This is the same card / cash / check / P2P method set introduced in the payment-collection storyboard referenced from Chapter 4's "Collecting Payment from the Homeowner" subsection — that subsection documents the technician-facing side of collection; this module holds the admin-facing provider implementations behind it.
  • A mark-paid job action — src/index.ts registers paymentReviewModule.jobActions with a single action, id mark-paid, whose onInvoke calls transitionJob(job, 'paid', ctx). This is the mechanism that would fire the completed → paid lifecycle transition from Chapter 2's state machine, gated by a hasPaymentRecord precondition: a partner-paid job (job.payer !== 'customer') is satisfied automatically, while a customer-paid job requires a settled row in the payments table (hasSettledPaymentForJob).
  • Handoff logic — domain/handoff.ts supports the deep-link handoff mechanics documented in Appendix B, "Handoff & Deep Links."
  • A reconciliation screen — screens/ReconciliationView.tsx is built and routed inside the module. 🟢 Built & Live — modules/payment-review/src/index.ts imports ./screens/ReconciliationView and routes it at payment-review through PaymentReviewScreen (wired in commit 2dc4fc7, 2026-08-17). The module is registered and the host injects its Supabase client (app/m/[moduleId].tsx); it opens at /m/payment-review and is not in the logo menu.

Getting the App on an Android Phone

The Android app is a sideload APK built on the office PC with npm run build:apk (run from app/apps/mobile in the main checkout, which holds the android/ folder and the .env config). The script checks the setup, builds, then verifies the APK; the finished APK is copied to the Desktop and installed on the phone by hand (allow "install unknown apps"). It is not a Play Store build (signed with a debug key), so it is for our own phones only. Full steps: app/docs/deployment.md, "Local Android APK build".
