Chapter 5 — Sales & Marketing

The Sales & Marketing module (modules/sales-marketing) covers review curation, marketing-post composition, and organic-post reporting. It registers with requiredRoles: ['sales', 'admin', 'owner'] — a field tech sees no Sales & Marketing entry. 🟢 Built & Live — modules/sales-marketing/src/index.ts imports ./screens/SalesMarketingRoot and routes it at sales-marketing (wired in commit 2dc4fc7, 2026-08-17), so a sales-role user lands on /m/sales-marketing after login and every screen in the walkthrough below is reachable from the running app.

What This Module Is, and Is Not

Despite the chapter title suggesting a full sales pipeline, this module does not implement lead intake, lead qualification, or scheduling screens. There is no UI here for driving a job through new → qualified → scheduled → assigned — those state transitions exist on the job spine (Chapter 2) and are exercised by other parts of the app (office/admin job creation and scheduling), not by anything in modules/sales-marketing. ⚪ Open Gap (Roadmap) A dedicated lead-pipeline UI inside this module is not built. What this module does build is the marketing side of the business: curating published customer reviews, composing social posts from real job evidence, and reporting on organic posting activity. The persona walkthrough below reflects that reality, not the pipeline language in this chapter's working title.

A Typical Day — Sales/Marketing

Dana runs sales and marketing for a two-truck outfit. Dana's day inside JobCore looks like this. Each stop below cross-references the real screen file and the job-lifecycle states in play, by name, per Chapter 2.

Morning: Review Library

Dana opens Review Library (screens/ReviewLibrary.tsx) 🟢 Built & Live to see which customer reviews from recently closed jobs are worth featuring. The list only ever shows reviews the office has already marked publish_ok = true — the screen has no code path to display an unpublished review, since ReviewLibraryRepository.list is scoped server-side by the reviews_select_sales policy (0012). Dana filters by minimum star rating, service id, and community id, and can nudge a strong review up the display order with the ↑/↓ reorder controls — the only write this screen performs (ReviewLibraryRepository.reorder, matching the reviews_sales_sort_whitelist_trg whitelist). Each row shows the reviewer's display name (or "Anonymous"), star rating, platform, and the linked job id — no commission, price-sheet, or payout data ever appears here, by construction, since Review exposes none of those fields.

Mid-Morning: Pitch Picker

Dana wants to build a post and opens Pitch Picker (screens/PitchPicker.tsx) 🟢 Built & Live, which presents four pitch angles: Service line, Community, Seasonal, and Before/after. Picking one hands the angle straight to Composer as a pre-filter for candidate assets — no navigator is involved; SalesMarketingRoot wires all four screens as state-driven sibling tabs (matching Field Tech's FieldTechRoot pattern from Chapter 4), so "navigate to Composer" here means a caller-supplied onNavigateToComposer prop switching the active tab.

Composing the Post

In Composer (screens/Composer.tsx) 🟢 Built & Live, Dana works through several honest guardrails:

  • Suggested caption is a template, not a claim. The suggestion is built from the pitch angle string alone — buildSuggestedCaption never reads a review's body or author name, so it can never fabricate a customer quote or a claim about work that wasn't done. It's always prefixed "Draft suggestion — edit before posting."
  • Asset selection is never trusted client-side. Every handleToggleAsset call round-trips through postDraftAssets.attach, which the database rejects unless the asset is approved_for_public = true and — for a review-backed asset — the underlying review is publish_ok = true (post_draft_assets_consent_check_trg, 0012). The screen only ever reflects what that trigger allowed.
  • Nothing posts before an explicit approve step. handleApprove saves the caption and calls postDrafts.approve; both export paths below stay disabled until approved is true.
  • Manual export (default, always available). Dana exports the selected images to the camera roll, copies the caption to the clipboard, opens the OS share sheet, then the screen logs the post intent to campaign_log with channel 'manual'. No API dependency, no App Review requirement.
  • Direct post (conditional). Only appears when the org has enabled the meta-publish social provider (an org-level config flag, default OFF). With the flag off, no provider resolves and zero network calls to the Meta Edge Function — or to graph.facebook.com — ever occur; the screen states plainly that direct posting is unavailable rather than showing a broken button. ⚪ Open Gap (Roadmap) Direct publishing additionally depends on Meta App Review approval for pages_manage_posts and instagram_content_publish — a multi-week external process this codebase cannot shorten (see modules/sales-marketing/README.md).

End of Day: Reporting

Dana checks Reporting (screens/Reporting.tsx) 🟢 Built & Live for three client-side aggregations pulled from real ports: posts by platform and month (from campaign_log), assets used vs. total marketing assets (from marketing_assets, counting approved_for_public), and reviews collected grouped by platform (from reviews). The screen carries a fixed notice: paid-ads reporting is out of scope for this module and additionally blocked until a Meta Pixel is installed on the website — installing the Pixel is the website owner's task, and this app must never install one itself. No query on this screen ever touches commissions, price_sheets, or payout_batches — this module's ports never expose those tables, so no such figure can appear here by construction.

Provider Extensibility

The SocialProvider interface (domain/providers/types.ts) is registered through a barrel (domain/providers/index.ts) that Composer and Reporting resolve through — never a concrete provider import. Today the barrel carries one provider, MetaPublishProvider (domain/providers/meta.ts). ⚪ Open Gap (Roadmap) A future LinkedIn, Nextdoor, or Google Business Profile provider is a new registered file, not a composer refactor — none of those exist yet.

Token Storage

🟢 Built & Live Long-lived Meta Page access tokens are stored server-side in Supabase only, in a table with zero authenticated-role RLS policies — reachable only by the meta-publish Edge Function's service-role key. They are never present in the app bundle and never stored in any client-visible or client-readable table; this module's own ports (SocialProviderRepository) deliberately expose only the org-level enabled flag, never a credential.
