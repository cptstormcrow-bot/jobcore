Sequence: completed → paid

The state machine's requirePaymentSettled precondition (packages/core/src/state-machine.ts) gates the state-completed → state-paid transition: if job.payer !== 'customer' the precondition passes automatically (partner-paid jobs need no payment record); otherwise it requires a payments row confirmed via hasSettledPaymentForJob. The paid → state-closed step that follows is a plain OFFICE-role transition with no precondition.

  1. Tech finishes the job on the Completion screen (modules/field-tech/src/screens/Completion.tsx) — after-photo + quality notes required client-side, then transitionJob(job, 'completed', ctx) fires. Job is now state-completed. 🟢 Built & Live
  2. Customer is handed off via a signed, expiring, single-job-scoped QR token (issue_handoff_token RPC, modules/payment-review/src/domain/handoff.ts) to the public handoff web app at web/handoff/. QR *rendering* is explicitly out of scope for this slice per the file's own TODO — only the token/URL is issued. 🟠 Built, Unverified
  3. Customer picks a payment method on the handoff site; the state machine settles into state-paid once a payments row reaches confirmed (webhook) or manual_confirmed (tech/office manual entry).
  4. Storyboarded, not built — a homeowner-satisfaction confirmation gate ahead of payment capture. No such gate exists in state-machine.ts, the payment-review module, or the handoff screens read for this slice. ⚪ Open Gap (Roadmap)
  5. Office marks the job state-paid → state-closed (plain OFFICE transition, no precondition).

The four payment methods

MethodProvider fileSettlement pathStatus
Card (Stripe) supabase/functions/stripe-webhook/index.ts Deno edge function verifies the Stripe-Signature header via manual HMAC-SHA256 (stripe-node unavailable in Deno edge), then on checkout.session.completed or payment_intent.succeeded updates the matching payments row (looked up by external_ref) to status='confirmed'. No card data (PAN/CVV/card_number) is ever read or logged. 🟠 Built, Unverified
Card (PayPal) supabase/functions/paypal-webhook/index.ts Deno edge function verifies via PayPal's server-side "Verify webhook signature" API (transmission-id/time/cert-url/auth-algo/sig headers + OAuth2 client-credentials token), then on PAYMENT.CAPTURE.COMPLETED or CHECKOUT.ORDER.APPROVED updates the matching payments row to status='confirmed'. 🟠 Built, Unverified
Cash modules/payment-review/src/domain/providers/cash.ts Not webhook-capable by design — buildHandoffAction returns null (no customer-facing handoff to drive). A tech confirms receipt in person; the resulting manual_confirmed status and confirmed_by are set elsewhere, in the tech-confirm UI flow (governed by the payments_tech_confirm_whitelist trigger, 0010_payment_review.sql, which restricts a non-admin caller to setting only status='manual_confirmed', confirmed_at, confirmed_by). 🟠 Built, Unverified
Check modules/payment-review/src/domain/providers/check.ts Identical pattern to Cash — no confirm method, buildHandoffAction returns null, manual tech/office confirmation via the same whitelist trigger. 🟠 Built, Unverified
P2P link (Venmo / CashApp / Zelle) modules/payment-review/src/domain/providers/p2p-link.ts Not webhook-capable — createP2PLinkProvider(config) builds a HandoffAction of kind link from an org-configured handle/URL (P2PLinkConfig); the bare P2PLinkProvider export has no config bound and always returns null — a caller needing a real handoff must use the factory. Settlement is manual confirmation, same whitelist-trigger path as Cash/Check. 🟠 Built, Unverified

Per-org provider enablement ("flip the switch in advance")

Which methods a given organization offers is controlled by the payment_providers table (supabase/migrations/0010_payment_review.sql): organization_id, provider_id, enabled boolean, and a client-safe config jsonb (a handle, a publishable key — never a secret key or any card data, enforced by naming convention plus a repo-wide grep check). RLS on this table is admin-only (payment_providers_admin_all policy: organization_id = current_org_id() AND is_org_admin()) — provider enablement/config is an organization-settings concern, never tech- or customer-facing. This is the fact Chapter 3's Admin persona cites for the payment-provider-setup callout: an admin flips these switches in advance, before any job reaches state-completed.

Web handoff screens (as-built)

Four screens exist today under web/handoff/src/screens/, sequenced by the review_requests.state column (0010_payment_review.sql, check constraint awaiting_payment | confirming | review | done):

  1. awaitingPayment.ts — lists the org's enabled providers; picking one requests that provider's HandoffAction — link/qr navigates the browser to action.url, in_app advances straight to confirming (mobile app takes over from there). Shown only when job.payer === 'customer' — a partner-paid job's router skips this screen entirely.
  2. confirming.ts — plain-text "waiting for confirmation" explainer, deliberately no polling/spinner in this slice; a later slice may add polling to auto-advance once settled.
  3. review.ts — reached after payment confirms (or via the partner-paid skip): 1-5 star rating, optional comment, explicit default-unchecked publish-consent checkbox, POSTs to /api/handoff/{token}/review, then two static public-review-platform links (Google, Facebook). Acceptance criterion: rendered copy/links are byte-identical regardless of rating — the rating is captured, never used to branch what's shown.
  4. done.ts — terminal thank-you screen with static business contact details.
