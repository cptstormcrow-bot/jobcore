How to Use This Manual

Each chapter in Part II (The Modules) is written from one of three lenses, chosen to fit what that module actually needs explained:

  • Task lens — walks a specific job the reader is trying to get done, step by step, screen by screen.
  • Feature lens — walks a screen or subsystem's capabilities without assuming a specific task in progress.
  • Informational lens — describes architecture, status, and constraints for content that has no day-in-the-life to walk (Chapter 6 is the clearest example).

Chapters 3 through 5 additionally open with an "A Typical Day" persona walkthrough — a narrative that follows one real role (Admin, Accountant, Service Technician, Sales/Marketing) through the module's real screens in the order a working day actually uses them. These walkthroughs cross-reference the job lifecycle states introduced in Chapter 2 by name, rather than re-explaining the state machine each time.

Note: Training is a roadmap item, not a chapter in this manual — there is no dedicated onboarding/training module or content to document yet.

Chapter 1 — What Is JobCore?

JobCore is a multi-tenant field-service platform: one codebase, one app, many independent organizations. Every organization's data is isolated at the database layer (Postgres row-level security keyed on organization_id), and every organization can turn on a different combination of feature modules without anyone shipping a new build just for them.

🟢 Built & Live — multi-tenant core, RLS isolation, job lifecycle

The JobcoreModule Contract

Every feature area in JobCore — Admin & Finance, Field Tech, Sales & Marketing, Payment & Review — is a self-contained module implementing one shared TypeScript interface, JobcoreModule (defined in packages/module-sdk/src/index.ts):

  • id — the module's stable identifier, e.g. 'admin-finance'
  • displayName — human-readable name shown in the app
  • requiredRoles — the Role[] that gates visibility and is mirrored in RLS policy
  • routes — the screens (real React components, not string names) the module contributes to the navigator
  • navEntries — icon, label, and sort order for each navigation entry
  • jobActions (optional) — buttons the module injects into the shared Job Detail screen
  • hooks (optional) — onJobStatusChange / onJobCompleted side-effect callbacks
  • migrations (optional) — module-owned Supabase tables
  • settings (optional) — a module-owned settings schema

Why Modules Are Compile-Time-Only

JobCore describes itself as "pluggable," but that word has an honest limit here: React Native cannot load or execute new native code at runtime, and both the App Store and Play Store forbid downloading and running new code after install. So "pluggable" means compile-time registration + runtime toggle — a module is a workspace package compiled directly into the app binary and added to a registry, and it is then enabled or disabled per organization through a config value, never through a runtime download. Adding a module is a build. Enabling one is a config change.

Two Independent Gating Axes

Whether a module is reachable in the running app depends on two independent gates, and both must pass:

Axis 1 — Compile-Time Registration

A module must be imported and registered in apps/mobile/src/modules.ts (lines 11–18) — the one file in apps/mobile permitted to name a specific module by id. As of this writing, three modules are registered there: admin-finance, field-tech, and sales-marketing. The fourth module, payment-review, is built but is NOT registered — its code exists and compiles, but registerModule() is never called for it, so it cannot appear in the app no matter what any organization enables. This is exactly Chapter 6's status.

Axis 2 — Runtime Per-Org Enablement

Independently of registration, each organization carries an enabled_modules text[] column (organizations.enabled_modules, supabase/0001_foundation.sql line 27). getEnabledModules(org, role) includes a module only if both the org's enabled_modules list contains the module's id and the requesting user's role is in the module's requiredRoles — fail-closed on both counts, so an empty requiredRoles list hides a module from everyone.

A module is only reachable by a given user when it clears both axes: registered at compile time, and enabled for that user's org and role at runtime. Chapter 6 is the concrete, worked example of a module that is built and would pass Axis 2 but fails Axis 1 today.

Chapter 2 — The Job Lifecycle & Platform Foundations

Every job in JobCore is a single state machine. One declarative transition table — TRANSITIONS in packages/core/src/state-machine.ts — is the only place transition legality is decided. No screen, module, or hook reimplements this logic with a scattered if; every UI affordance asks canTransition instead. 🟢 Built & Live

The Job Spine

The main line runs:

new → qualified → scheduled → assigned → accepted → en_route → in_progress → completed → paid → closed

Three branches leave the main line: declined (a rejected field assignment, routed back to the office), needs_reschedule (raised from any pre-field state and resolved back to scheduled), and cancelled (office-only, from any state before field work starts).

The States, in Lifecycle Order

new

A job's starting state. Entered when a lead is captured; the office qualifies it next.

qualified

The office has vetted the lead as a real, schedulable job.

scheduled

The office has put the job on the calendar. This is also the state that declined and needs_reschedule both resolve back to.

assigned

The office has assigned the job to a field tech. From here the field side takes over: the tech can move the job to accepted or declined.

accepted

The assigned tech has accepted the job.

en_route

The tech has started driving to the job. This is also the last state from which the office can still cancel the job — see Cancellation Window Closes at en_route below.

in_progress

The tech is on site and working. Entering this state requires the start-checklist precondition to be satisfied first.

completed

The tech has finished the work. Entering this state requires the completion-evidence precondition (after-photos and quality notes) to be satisfied first.

paid

The office has recorded payment. Entering this state requires the payment-settled precondition when the customer is the payer.

closed

The job is fully closed out. Terminal state on the main line.

declined

A field tech has declined an assigned job. Routes back to scheduled for office reassignment — it does not return to assigned directly.

needs_reschedule

Raised by the field side from scheduled, assigned, or accepted when the existing schedule no longer works. The office resolves it back to scheduled.

cancelled

Office-only. Reachable from new, qualified, scheduled, assigned, or accepted — i.e. any state before the tech goes en route. Once the job reaches en_route, it can no longer be cancelled through this table.

Role Gating: OFFICE vs. FIELD

OFFICE = owner, admin. FIELD = owner, admin, tech (office roles retain oversight over every field-side transition). A sales role has no job-transition authority in this table at all — Sales & Marketing's role in the lifecycle is upstream of it (see Chapter 5).

The source file is explicit that this role table is not published verbatim in the Master Spec — it is a reasonable inference from who performs which lifecycle step, called out in code rather than presented silently as spec text. If it's ever wrong, the fix is additive: adjust the roles array on the affected row; the table stays the single source of legality.

The Three Preconditions

Start checklist (en_route → in_progress)
Fails closed with "in_progress requires a submitted start checklist" unless ctx.hasSubmittedStartChecklist reads true.
Completion evidence (in_progress → completed)
Requires both an after-photo (ctx.hasAfterPhotos) and quality notes (ctx.hasQualityNotes); either missing fails closed with a distinct reason string.
Payment settled (completed → paid)
Only enforced when job.payer === 'customer' — in that case ctx.hasPaymentRecord must read true, or the transition fails closed with "paid requires a payment record when payer is the customer". Non-customer payers pass through with no check.

All three probes are synchronous by contract: a probe that returns a Promise is treated as unsatisfied (fail closed), the same as an undefined probe — canTransition never awaits.

Cancellation Window Closes at en_route

The cancelled branch is reachable only from new, qualified, scheduled, assigned, or accepted. There is no en_route → cancelled row in the table, and none for any state after it. Once a tech has gone en route, the office can no longer cancel the job through the state machine — the operational read is that dispatch is treated as committed the moment the tech starts driving.

Device-Clock Payroll Stamping

On every applyTransition call the state machine dual-stamps two clocks: occurredAt from the device clock (ctx.now()) and syncedAt from the server clock (ctx.serverNow()), falling back to occurredAt when no server clock is wired up. occurredAt — the device clock — is the payroll-relevant input, not the server clock. Three lifecycle timestamps are stamped from it directly onto the job record: enRouteAt, inProgressAt, and completedAt, set respectively when the job transitions into en_route, in_progress, or completed. Clock skew between the two stamps is evaluated against a configurable threshold (ctx.clockConfig, defaulting to DEFAULT_CLOCK_CONFIG) and recorded, not enforced as a blocker.

Audit Log and the metadata Workaround

Every successful transition writes exactly one insert-only audit_log row through the optional ctx.writeAudit sink — optional so that packages/core stays zero-dependency and never learns what Supabase is. When no sink is wired up, no row is written and nothing throws; when a sink is wired up, the write is awaited, so a failing sink rejects the whole transition rather than silently dropping the row.

The row records fromState, toState, occurredAt, syncedAt, skewMs, and skewed — but the shipped audit_log table (supabase/0001_foundation.sql, lines 45–56) has no dedicated columns for any of them. All five ride inside the table's existing metadata jsonb column instead. Rows are insert-only and never updated. 🟢 Built & Live
