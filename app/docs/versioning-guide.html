1. In 30 seconds

The idea: every change saved to the project (a "commit") has a label at the start of its description, like feat: or fix:. When a milestone is finished you run one command, npm run release. It reads those labels since the last release, works out the new version number, updates the files that hold it, writes a change list, and stamps the point in history with a tag such as v0.3.0. Nothing is sent over the internet.

  • feat: = new feature = middle number goes up (0.2.0 to 0.3.0).
  • fix: or perf: = repair or speed-up = last number goes up (0.3.0 to 0.3.1).
  • docs:, chore:, test: and friends = no release.
  • Preview first with npm run release:dry. It changes nothing.

2. What a version number means

A version looks like MAJOR.MINOR.PATCH, for example 0.3.1. This scheme is called SemVer (semantic versioning). Each of the three numbers has a job:

  • PATCH (last number): small repairs and speed-ups. Nothing new to learn.
  • MINOR (middle number): something new was added. Resets PATCH to 0.
  • MAJOR (first number): a big, possibly incompatible change. Resets the other two to 0.
0.2.0 then a feature 0.3.0 then a fix 0.3.1 then a feature 0.4.0

Alongside the version, each release also adds one to two build counters: versionCode for Android and buildNumber for iOS. These are plain counting numbers the phone stores use to tell builds apart. They go up by 1 every release and are shown in the app as "build N".

The master copy of the version lives in expo.version inside apps/mobile/app.json. The release command copies it into apps/mobile/package.json and the top-level package.json so all three agree.

3. Below 1.0, and going to 1.0

A version starting with 0 means "still being shaped". By convention, while the first number is 0, even a breaking change only bumps the middle number, not the first one. JobCore follows that: below 1.0 a breaking change bumps MINOR.

Going to 1.0 is a decision, not an automatic step. The release command never produces 1.0 by itself while below 1.0. When you decide JobCore is ready to be called a stable 1.0, that promotion is done by hand. Ask a developer or Claude to do it, and say so explicitly. Once the number is 1 or higher, a breaking change bumps MAJOR as normal.

4. Commit message cheat sheet

The first line of a commit message is the "subject". Its format is type: description or type(area): description. Add ! before the colon for a breaking change, or put a line starting BREAKING CHANGE: in the commit's longer body.

When several commits are in play, the biggest bump wins (a feature beats a fix). Commit subjects beginning Merge, Revert, fixup! or squash! are skipped silently without a warning.

5. The routine, step by step

Do this at the end of a milestone, from the app folder of the project.

  1. Finish the work and make the milestone commit as usual.
  2. Preview what a release would do (safe, writes nothing): 
    npm run release:dry
  3. Read the output: it shows the plan (old tag to new version, bump level, number of commits) and the draft change list. If it says nothing to release, there were no feat/fix/perf/breaking commits, and you are done.
  4. Happy with it? Do the real thing: 
    npm run release
  5. It prints Released vX.Y.Z (committed and tagged locally; not pushed).
  6. Write the build report for the milestone (it comes after the release, so it can quote the new version).
  7. Build the APK when needed (see section 8).

Order matters: release after the milestone commit, before the build report. The release command makes its own commit, so the working copy of the four release files must be clean first.

6. What npm run release changes

It does these things, in order:

  1. Finds the last v* tag and reads every commit since then.
  2. Works out the bump (section 4) and the new version.
  3. Edits four files:
FileChange
apps/mobile/app.jsonexpo.version set to the new version; android.versionCode +1; ios.buildNumber +1
apps/mobile/package.jsonversion set to the new version
package.json (app root)version set to the new version
CHANGELOG.mdNew dated section added at the top, grouped as Breaking, Features, Fixes, Performance
  1. Makes one commit named chore(release): vX.Y.Z containing just those four files.
  2. Creates a tag vX.Y.Z on that commit.

The command never pushes. The commit and tag stay on this computer. With --dry (that is, npm run release:dry) nothing is written, committed or tagged.

Any branch can release. The new version is the larger of: (a) what the commits since this branch's last tag compute to, and (b) the highest v* tag anywhere in the repository bumped by the same level. This stops two branches from handing out the same number. If the winning tag already exists, the command stops (see section 11).

7. Where you see the version in the app

  • The gear menu (⚙): the very bottom row of the menu, on every screen that has the gear. It looks like Version 0.3.0 (build 5).
  • The Settings screen: the same text appears there.
  • If the app cannot work out its version, the text reads Version unknown. If there is no build number, it reads just Version 0.3.0.

The label is built by formatVersionLabel.ts, so both places always match.

8. The APK build script messages

An APK is the installable Android app file. The script apps/mobile/scripts/build-apk.ps1 runs a "preflight" (a checklist) before building. Two parts relate to versions.

SYNCED lines

Android keeps its own copy of the version in android/app/build.gradle, which is not saved in git. If it differs from app.json, the script fixes it and prints:

SYNCED: versionCode 3 -> 4
SYNCED: versionName 0.3.0 -> 0.4.0

(numbers will differ). This only appears when something was out of date. What to do: nothing. It is the script helping. No SYNCED lines means everything already matched.

The WARN line

WARN: 3 releasable commit(s) since v0.3.0 — run 'npm run release' before building a release APK.

It means there are feat, fix, perf or breaking commits since the last tag that have not been given a version yet. The build still goes ahead; this is only a reminder. What to do: stop, run npm run release, then build so the APK carries the right number. If there is no v* tag at all, the warning stays silent.

9. The commit-msg hook

A "hook" is a small script git runs automatically. The commit-msg hook checks the first line of each new commit and, if it does not follow the format in section 4, prints:

WARNING: commit subject is not Conventional Commits, so it will not drive a version bump.
  Allowed types: feat fix perf docs chore test refactor ci style build revert
  Example: feat(scope): add thing

It only warns and never blocks a commit. Merge, Revert, fixup! and squash! subjects are not warned about. Turn it on once per copy of the project:

git config core.hooksPath .githooks

10. Worked examples

Example A: a feature and a fix

Last tag v0.2.0. Commits since: feat: add photo upload, fix: crash on empty list, docs: update notes.

The feature wins. Result: 0.3.0. The change list shows one Feature and one Fix; the docs commit is not listed.

Example B: only fixes and housekeeping

Last tag v0.3.0. Commits: fix: wrong total on invoice, perf: faster job list, chore: tidy.

Result: 0.3.1 (patch).

Example C: nothing releasable

Last tag v0.3.1. Commits: docs: typo, test: add case, refactor: rename file.

The command prints nothing to release and changes nothing.

Example D: a breaking change before 1.0

Last tag v0.3.1. Commit: feat(jobs)!: change status names.

Below 1.0 a breaking change counts as minor. Result: 0.4.0, with the item listed under Breaking.

Example E: another branch is ahead

This branch's last tag is v0.2.0 and it has a feat, so it computes 0.3.0. But another branch already tagged v0.3.0, the highest tag in the repo. The rule bumps that highest tag by the same level, giving 0.4.0.

11. Troubleshooting

Messages are printed to the screen exactly as below, and the command stops with nothing changed (except where noted).

MessageMeaningFix
No v* tag found: release needs a baseline. Tag v0.2.0 on the 0.2.0 release commit (`git tag -a v0.2.0 <sha> -m "v0.2.0"`, find sha with `git log -S'"version": "0.2.0"' --format=%H -- apps/mobile/app.json`).The tool counts commits since the last tag, but this copy of the repo has no tag yet.Run the find-sha command from the message to get the commit's ID, then the tag command with that ID. Tags are local only, so each computer that releases needs the baseline tag. The baseline is v0.2.0.
Release files have uncommitted changes: followed by a list of filesOne of the four release files (the two package.json files, app.json, CHANGELOG.md) has unsaved edits. The release commit would sweep them in.Commit or discard those edits, then run again. Other unrelated dirty files do not block it.
Tag vX.Y.Z already exists; aborting.The new number it picked is already used as a tag.Look at git tag -l "v*". Usually you are on a branch behind, or the release was already done. Do not delete tags to force it; ask a developer.
nothing to release (not an error)No feat, fix, perf or breaking commits since the last tag.Nothing to do.
WARN: Non-conventional subject (ignored): abc1234 Some message (a warning, the command keeps going)A commit's first line did not follow section 4, so it was skipped.Nothing required. If it should have counted, the fix is a new correctly labelled commit.

If git itself prints some other error, the command passes that text along unchanged and exits; copy it to a developer or Claude.

12. Glossary

Commit
A saved snapshot of the project with a short description.
Subject
The first line of a commit's description. The label that drives versions is here.
Conventional Commits
A simple naming habit: type: description.
SemVer
MAJOR.MINOR.PATCH numbering, explained in section 2.
Tag
A named bookmark on a commit, such as v0.3.0. Here they are never pushed.
Baseline
The first tag, v0.2.0, that counting starts from.
Breaking change
A change that can break something that worked before.
Dry run
A rehearsal that shows what would happen without doing it. npm run release:dry.
versionCode / buildNumber
Build counters for Android / iOS, +1 per release.
Changelog
The file CHANGELOG.md, a running list of what changed in each version.
Hook
A script git runs automatically at certain moments.
APK
The installable Android app file.
Preflight
The checklist the APK script runs before building.
Push
Sending local work to a shared online copy. The release command never does this.
